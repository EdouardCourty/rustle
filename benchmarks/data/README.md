# Data for the website

Structured copies of the published numbers, read by <https://github.com/EdouardCourty/rustle-site> (the source of <https://rustleproxy.dev>) at the latest release tag. The website never parses `README.md` or `RESULTS.md`: these files are the contract. They are committed, regenerated by tools, validated against JSON Schemas, and checked by `make check` (`make data-check`) and CI, so they cannot go stale.

## From the raw runs to the published numbers

Nothing published is typed or copied by hand: every number is a function of the raw runs.

```text
bench-client (JSON document per test)         benchmarks/generator
      + raw counters before / after           run-bench.sh, run-remote.sh (cgroup CPU, /proc status and stat, network counters)
  -> tools/record.py                          saturation and validity verdicts            -> run.json   (schema/run.schema.json)
  -> manifest = campaign.json `sources.runs`  which run plays which part                  (run-campaign.sh / run-scaling.sh write fragments)
  -> tools/aggregate.py                       best clean sweep level, unsupported, scaling -> <id>/benchmarks.json
  -> tools/render.py                          pure functions of benchmarks.json:          charts benchmarks/charts/*.svg,
                                              the README table and numbers, the tables and numbers of benchmarks/documentation/RESULTS.md
```

`make data` runs the last two steps from the committed runs; `make bench-publish` (`run-all.sh`) runs a campaign first. `make data-check` regenerates all of it and fails when a committed file differs, so none of it can drift.

```text
benchmarks/data/
  index.json                       every campaign, and which one is `latest`
  README.md                        this file
  schema/
    index.schema.json              JSON Schema (2020-12) of each file, shared by all campaigns
    campaign.schema.json
    benchmarks.schema.json
    proxies.schema.json
  2026-10-28/                      one folder per campaign, named like benchmarks/published/<id>/
    campaign.json                  conditions, sources, limits, notes (hand-edited, checked against the runs)
    proxies.json                   the compared proxies as they were run (hand-edited, checked)
    benchmarks.json                the numbers (generated)
documentation/
  config.json                      reference of every config key (by hand)
  config.schema.json               its JSON Schema (by hand)
```

| File | What | Written by |
|---|---|---|
| `index.json` | the campaigns and `latest` | by hand: one entry per campaign |
| `<id>/campaign.json` | hardware, network, software, seed, repeats, the manifest of the raw runs (`sources.runs`), unsupported proxies, limits, notes on points | by hand, when a campaign is published (the manifest from the fragments of `run-campaign.sh`) |
| `<id>/proxies.json` | competitor versions, tuning, protocols, project URLs, characteristics | by hand |
| `<id>/benchmarks.json` | every published number with its conditions | `tools/aggregate.py --write` (`make data`), also run by `make bench-publish` |
| `../../documentation/config.json` | reference of every config key: type, default, description, `live` or `restart` | by hand, next to the code |
| `schema/*.schema.json` | the contract, one schema per file kind, including `run.schema.json` for the raw `run.json` of `benchmarks/published/*/runs/**` and `benchmarks/results/**` | by hand |
| `../../documentation/config.schema.json` | the contract of `config.json` | by hand |

## Campaigns are self-contained and not comparable

Each campaign folder stands alone: its conditions, its competitors' versions and tuning (they change from one campaign to the next), its numbers. **Numbers are not comparable across campaigns**: the protocol, the versions and the hardware change (see "Do not compare numbers across bench protocol changes" in `AGENTS.md`). The website shows `latest`; a history page lists campaigns but must not chart a metric across them. `benchmarks.json` carries only `campaign: "<id>"`; the conditions are in the same folder's `campaign.json`, never duplicated.

`tests[].chart` names a file of `benchmarks/charts/`, which holds the charts of the **latest** campaign only: use it for `latest` and ignore it for older campaigns.

## JSON Schema

The producer owns the contract. Each file kind has a schema in dialect 2020-12; the website reads the schemas at the same release tag as the data and turns them into validators and types at build time (zod's `z.fromJSONSchema`), so a data file that does not fit its schema breaks the website build instead of publishing wrong numbers.

* **Pointer.** Every data file starts with `"$schema"`, a path relative to the file: `./schema/index.schema.json` for `index.json`, `../schema/<name>.schema.json` for the files of a campaign, `./config.schema.json` for `documentation/config.json`. Editors use it for completion; the check requires it to be exact.
* **`$id`.** `https://raw.githubusercontent.com/EdouardCourty/rustle/main/<path of the schema>`. It is an identity, not a place readers fetch from: readers use the relative pointer, so they get the schema that matches the tag they read. `main` in the identifier keeps it stable across releases; it never has to resolve.
* **Strict.** `additionalProperties: false` everywhere, except `campaign.json`'s `test_notes` (a map keyed by test id, open by design). `schema_version` is a `const` (currently `1`): a breaking change bumps it in the schema and the data, and readers refuse a version they do not know. Adding an optional field, a new proxy id or an enum value is additive and keeps the version.
* **Keywords**: plain ones only, see [Validation](#validation).
* **Per-proxy maps** (`values`, `at_conns`, `status`, `flags`) have one property per known proxy id. A property is optional in the schema (a campaign may not include every proxy); `make data-check` requires exactly the proxies of the campaign's `proxies.json`.

## Validation

`make data-check` (run by `make check` and the CI `website data` job) does two things:

1. `make schema-check`: [`check-jsonschema`](https://pypi.org/project/check-jsonschema/) validates every data file against its schema and every schema against the JSON Schema metaschema (`benchmarks/data/*/campaign.json` against `campaign.schema.json`, and so on, with globs, so a new campaign needs no list to edit; `documentation/config.json` against `documentation/config.schema.json`). It uses `check-jsonschema` if it is on the `PATH`, else `uvx` or `pipx run` at the pinned version, else it stops with an install hint (`pipx install check-jsonschema==<version>`). The version is pinned in one place, `CHECK_JSONSCHEMA_VERSION` in the `Makefile`; CI installs it with `make install-schema-tool`.
2. `tools/check.py`: everything a JSON Schema cannot say. The charts, the README table and numbers and the tables and numbers of `benchmarks/documentation/RESULTS.md` are regenerated from `benchmarks.json` and compared with the committed files, and `benchmarks.json` of every campaign is regenerated from its raw runs by `tools/aggregate.py` and compared (so `make data` is idempotent and nothing is typed by hand); exact `$schema` pointers; `index.json` lists `latest`, has unique ids that match the folders and each file's own `id` / `campaign`, and its `date`, `rustle_version` and `proxies` agree with the campaign's files; every by-proxy map of `benchmarks.json` has exactly the campaign's proxies; project URLs are well-formed `https`; `campaign.json`'s `seed`, `repeats`, `proxy_cores` and `auth` are what the runs say and no run is dated more than a day from the campaign; for `latest` only (they describe the current setup): `proxies.json` versions against the table of `FAIRNESS.md`, TLS and HTTP/2 support against the `# bench-ports:` lines of `proxies/*/Dockerfile`, each chart file exists, and the kTLS saving and cost quoted by the documentation are the ones of `ktls[]`.

`make test-tools` (in `make check` and the CI job) runs the unit tests of the bench tools (`benchmarks/tools/tests/`: the saturation and validity logic and the parsing of the raw counters of `record.py`, on figures of the 2026-10-28 campaign; the best-level rule and the statuses of `aggregate.py`; the placeholders of `RESULTS.md`), and `cargo test -p bench-client` the JSON the generator prints.

No dependency is added to the Rust crate (the generator writes its JSON by hand) or to the Python tools (stdlib only; the schema validation is the off-the-shelf tool).

Keep the schemas to plain keywords: `type`, `enum`, `const`, `required`, `properties`, `additionalProperties`, `items`, `minItems`, `minimum`, `minLength`, `pattern`, `format: "uri"`, `anyOf` (nullable values are `anyOf` of the type and `{ "type": "null" }`) and local `$ref` to `$defs`, with the annotations `$schema`, `$id`, `title` and `description` (every property has a `title` and a `description`, by convention). The website turns the schemas into validators with zod's `fromJSONSchema`, and its build fails on anything it cannot convert (`if`/`then`/`else`, `patternProperties`, `$dynamicRef`, remote references): a schema change should be tried against the site (`RUSTLE_LOCAL=../rustle`) before a release.

## Shapes

```text
index.json       { $schema, schema_version, latest, campaigns[{ id, date, rustle_version, proxies[ids], path }] }

<id>/campaign.json
                 { $schema, schema_version, id, date, rustle_version, commit,
                   hardware{provider, generator, proxy, origin_sink : {server, cpu, cores, threads, role}},
                   network{kind, mtu, nominal_gbit_s, measured_gbit_s, measured_with},
                   software{os, kernel, docker, governor}, seed, repeats, run_seconds, proxy_cores, auth,
                   noise_pct{min, max}, protocol, fairness, results,
                   sources{runs[{ role: main|ws|ktls|scaling|flood, proxy, transport, cores?, run }]}, unsupported?{transport: [ids]},
                   limits[{ id, text }], test_notes{ test id: text } }

<id>/proxies.json
                 { $schema, schema_version, campaign,
                   proxies[{ id, name, version, build, repository?, website?, settings[],
                             protocols{tls, h2, websocket}, characteristics[], fairness }] }

<id>/benchmarks.json
                 { $schema, schema_version, campaign, tests[], scaling[], ktls[] }
  tests[]        { id, transport, label, unit, direction, conditions, chart,
                   values{proxy: number|null}, at_conns{proxy: int|null},
                   status{proxy: "ok"|"unsupported"|"not_measured"|"invalid"},
                   flags{proxy: ["proxy_unsaturated"|"harness_saturated"]} }
  scaling[]      { id, label, unit, direction, conditions, not_measured[ids],
                   points[{ cores, values{proxy}, at_conns{proxy}, flags{proxy} }] }
  ktls[]         { id, label, unit, direction, user_space, ktls }

documentation/config.json { $schema, schema_version,
                   tables[{ name, description, keys[{ key, path, type, values?, default, description, reload }] }] }
```

Values come from the raw runs listed in `campaign.json` (`tools/aggregate.py`): for each test, the best sweep level without a client error. A number is never rounded up; the website formats it. Besides `values`, a test carries the figures the tables of `RESULTS.md` show: `cpu_us` (µs of proxy CPU per request or message), `cpu_ms_per_gb` (ms of proxy CPU per decimal gigabyte, tunnels and 64 KB frames), `p99_ms` (WebSocket) and `proxy_util`; scaling points carry `proxy_util` and `origin_util`.

* `id` of a test is `<transport>-<test>`, stable. `transport` is `plain`, `tls`, `tls-full-handshake`, `h2`, `ws` or `ws-tls`. `direction` says which way is better. `unit` is `req/s`, `msg/s`, `Gbit/s`, `MB`, `µs/req`, `µs/msg` or `ms`.
* `values[proxy]` is `null` when there is no number, and `status[proxy]` says why: `unsupported` (the proxy cannot do it: no TLS or HTTP/2 listener, no WebSocket), `not_measured` (it could, but was not run), `invalid` (client errors: not publishable). A missing result is shown as unsupported or failed, never as zero.
* `at_conns` is the connection count of the best level (`null` for the memory tests, where the count is in the label).
* `flags`: `proxy_unsaturated` means the proxy used less than 90 % of its core at that level (the harness or the test network set the number); `harness_saturated` means the origin or the sink was above 90 %. The editorial reading of such a point (for instance that the test network limits rustle) is `campaign.json`'s `test_notes[<test id>]`.
* `conditions` is a sentence to print next to the number; the rest of the conditions (hardware, network, seed, repeats, noise, limits) is in `campaign.json`.
* `ktls[]` compares `tls.ktls = false` (`user_space`) with `true` (`ktls`) on rustle, on the tests of the TLS matrix.
* `proxies.json`: `version` is the one in the table of `FAIRNESS.md`; `repository` and `website` are optional `https` URLs, present only when `FAIRNESS.md`, `RESULTS.md` or `proxies/<id>/Dockerfile` states them (a missing one is left for the author to add by hand). `characteristics` are facts quoted from `FAIRNESS.md` and `RESULTS.md`; there is no "does better" claim because nothing in the published results backs one.
* `documentation/config.json`: `type` is `string`, `integer`, `boolean`, `duration` (a string such as `"1m"`), `string list`, `integer list` or `enum` (with `values`); `reload` is `live` (applied to new connections by `rustle reload`) or `restart`. The file is maintained by hand: a config key added or changed in the proxy is edited there, with the same wording as `config.toml.example` and the README; the proxy crate knows nothing about it.

## The raw runs

`run.json` (`schema/run.schema.json`), one per run directory `<label>/<remote-auth-on|auth-on>/<timestamp>/`: the setup of the run (`proxy`, `transport`, `matrix`, `host`, `auth`, `seed`, `repeat`, `workers`, `params`) and `results[]`, one per test and connection level in the order they were measured: `test`, `mode`, `workload`, `err_kinds`, `measured` (the generator's medians), `generator` (its own cost and the TLS footing), `proxy` (CPU per run, memory, TCP counters), `saturation` (utilisations and flags), `valid` and `problems`. `bench-client` prints the workload and the measurements as one JSON document; the harness scripts take raw snapshots of the machines' counters before and after each test and hand both to `tools/record.py`, which computes the rest (CPU per run, saturation, validity) and appends the result. Nothing reads a text line back.

## Publishing a campaign

1. Create `benchmarks/data/<id>/` (the same `<id>` as `benchmarks/published/<id>/`) with a `campaign.json` and a `proxies.json` (copy the previous ones and edit: versions, hardware, `unsupported`, `test_notes`, `limits`), and add the campaign to `index.json` with `latest` set to it.
2. `make bench-publish` (`run-all.sh`; `REPORT_ONLY=1` to use the newest manifests of `benchmarks/results/`) runs the campaigns, which write manifest fragments (`results/campaign-<ts>.json`, `results/scaling-<ts>.json`), then lists the points that are not clean and writes `benchmarks/data/<id>/benchmarks.json`, the charts, the README and `RESULTS.md` numbers (`CAMPAIGN=<id>` to target a folder other than `latest`).
3. Copy the runs you publish to `benchmarks/published/<id>/runs/` and put the manifest (the fragments' `runs`) in the campaign's `campaign.json` `sources`, so that `make data` reproduces everything from what is committed. `make data-check` must be clean.
4. Review the diff, commit.
