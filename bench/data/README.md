# Data for the website

Structured copies of the published numbers, read by <https://github.com/EdouardCourty/rustle-site> (the source of <https://rustleproxy.dev>) at the latest release tag. The website never parses `README.md` or `RESULTS.md`: these files are the contract. They are committed, regenerated by tools, validated against JSON Schemas, and checked by `make check` (`make data-check`) and CI, so they cannot go stale.

```text
bench/data/
  index.json                       every campaign, and which one is `latest`
  README.md                        this file
  schema/
    index.schema.json              JSON Schema (2020-12) of each file, shared by all campaigns
    campaign.schema.json
    benchmarks.schema.json
    proxies.schema.json
  2026-10-28/                      one folder per campaign, named like bench/published/<id>/
    campaign.json                  conditions, sources, limits, notes (hand-edited, checked against the runs)
    proxies.json                   the compared proxies as they were run (hand-edited, checked)
    benchmarks.json                the numbers (generated)
docs/
  config.json                      reference of every config key (generated, one per release)
  config.schema.json               its JSON Schema (generated)
```

| File | What | Written by |
|---|---|---|
| `index.json` | the campaigns and `latest` | by hand: one entry per campaign |
| `<id>/campaign.json` | hardware, network, software, seed, repeats, which indexes make up the campaign, unsupported proxies, limits, notes on points | by hand, when a campaign is published |
| `<id>/proxies.json` | competitor versions, tuning, protocols, project URLs, characteristics | by hand |
| `<id>/benchmarks.json` | every published number with its conditions | `tools/site-data.py --write` (`make data`), also run by `make bench-publish` |
| `../../docs/config.json` | reference of every config key | `UPDATE_CONFIG_DOCS=1 cargo test -p rustle config_reference` |
| `schema/*.schema.json` | the contract, one schema per file kind | by hand |
| `../../docs/config.schema.json` | the contract of `config.json` | generated by the same test: its table names and key paths come from the config structs |

## Campaigns are self-contained and not comparable

Each campaign folder stands alone: its conditions, its competitors' versions and tuning (they change from one campaign to the next), its numbers. **Numbers are not comparable across campaigns**: the protocol, the versions and the hardware change (see "Do not compare numbers across bench protocol changes" in `AGENTS.md`). The website shows `latest`; a history page lists campaigns but must not chart a metric across them. `benchmarks.json` carries only `campaign: "<id>"`; the conditions are in the same folder's `campaign.json`, never duplicated.

`tests[].chart` names a file of `docs/benchmarks/`, which holds the charts of the **latest** campaign only: use it for `latest` and ignore it for older campaigns.

## JSON Schema

The producer owns the contract. Each file kind has a schema in dialect 2020-12; the website reads the schemas at the same release tag as the data and turns them into validators and types at build time (zod's `z.fromJSONSchema`), so a data file that does not fit its schema breaks the website build instead of publishing wrong numbers.

* **Pointer.** Every data file starts with `"$schema"`, a path relative to the file: `./schema/index.schema.json` for `index.json`, `../schema/<name>.schema.json` for the files of a campaign, `./config.schema.json` for `docs/config.json`. Editors use it for completion; the check requires it to be exact.
* **`$id`.** `https://raw.githubusercontent.com/EdouardCourty/rustle/main/<path of the schema>`. It is an identity, not a place readers fetch from: readers use the relative pointer, so they get the schema that matches the tag they read. `main` in the identifier keeps it stable across releases; it never has to resolve.
* **Strict.** `additionalProperties: false` everywhere, except `campaign.json`'s `test_notes` (a map keyed by test id, open by design). `schema_version` is a `const` (currently `1`): a breaking change bumps it in the schema and the data, and readers refuse a version they do not know. Adding an optional field, a new proxy id or an enum value is additive and keeps the version.
* **Keywords used** (so the schemas stay portable): `type`, `enum`, `const`, `required`, `properties`, `additionalProperties`, `items`, `minItems`, `minimum`, `minLength`, `pattern`, `format: "uri"`, `anyOf` (for nullable values: `anyOf` of the type and `{ "type": "null" }`), local `$ref` to `$defs`, and the annotations `$schema`, `$id`, `title`, `description`. No `if`/`then`/`else`, `patternProperties`, `$dynamicRef` or remote references. Every property has a `title` and a `description`.
* **Per-proxy maps** (`values`, `at_conns`, `status`, `flags`) have one property per known proxy id. A property is optional in the schema (a campaign may not include every proxy); `make data-check` requires exactly the proxies of the campaign's `proxies.json`.

## Validation

`make data-check` (`tools/site-data.py --check`, run by `make check` and the CI `website data` job) uses `tools/schemalite.py`, a stdlib validator of exactly the keywords above (a schema using another keyword fails the check, so a schema cannot rely on something nothing enforces). It checks:

* the schemas themselves (2020-12 dialect, `$id`, `schema_version` const, `title`/`description` on every property);
* every file: valid JSON, exact `$schema` pointer to an existing schema, conforms to its schema;
* `index.json`: `latest` is listed, ids are unique and match their folder and each file's own `campaign`/`id` field, `date`, `rustle_version` and `proxies` agree with the campaign's files, no folder is missing from the index;
* `benchmarks.json` is exactly what the indexes in `campaign.json` generate (never stale), and `campaign.json`'s `seed`, `repeats`, `proxy_cores` and `auth` are what the runs say;
* for `latest` only: `proxies.json` versions against the table of `FAIRNESS.md`, TLS and HTTP/2 support against the `# bench-ports:` lines of `dut/*/Dockerfile`, and that each chart file exists (those describe the current setup);
* `docs/config.json` against `docs/config.schema.json`; `cargo test` keeps both files equal to what the code generates.

No dependency is added to the Python tools or to the Rust crate.

## Shapes

```text
index.json       { $schema, schema_version, latest, campaigns[{ id, date, rustle_version, proxies[ids], path }] }

<id>/campaign.json
                 { $schema, schema_version, id, date, rustle_version, commit,
                   hardware{provider, generator, proxy, origin_sink : {server, cpu, cores, threads, role}},
                   network{kind, mtu, nominal_gbit_s, measured_gbit_s, measured_with},
                   software{os, kernel, docker, governor}, seed, repeats, run_seconds, proxy_cores, auth,
                   noise_pct{min, max}, protocol, fairness, results,
                   sources{main, ws?, ktls?, scaling?[{cores, index}]}, unsupported?{transport: [ids]},
                   limits[{ id, text }], test_notes{ test id: text } }

<id>/proxies.json
                 { $schema, schema_version, campaign,
                   proxies[{ id, name, version, build, repository?, website?, settings[],
                             protocols{tls, h2, websocket}, characteristics[], fairness }] }

<id>/benchmarks.json
                 { $schema, schema_version, campaign, tests[], scaling[], ktls[] }
  tests[]        { id, transport, label, unit, direction, conditions, chart,
                   values{proxy: number|null}, at_conns{proxy: int|null},
                   status{proxy: "ok"|"unsupported"|"not_measured"|"invalid"},
                   flags{proxy: ["proxy_unsaturated"|"harness_saturated"]} }
  scaling[]      { id, label, unit, direction, conditions, not_measured[ids],
                   points[{ cores, values{proxy}, at_conns{proxy}, flags{proxy} }] }
  ktls[]         { id, label, unit, direction, user_space, ktls }

docs/config.json { $schema, schema_version, version,
                   tables[{ name, description, keys[{ key, path, type, values?, default, description, reload }] }] }
```

Values come from the same campaign indexes and the same rule as the README table and the charts (`tools/benchlib.py`): for each test, the best sweep level without a client error. A number is never rounded up; the website formats it.

* `id` of a test is `<transport>-<test>`, stable. `transport` is `plain`, `tls`, `tls-full-handshake`, `h2`, `ws` or `ws-tls`. `direction` says which way is better. `unit` is `req/s`, `msg/s`, `Gbit/s`, `MB`, `µs/req`, `µs/msg` or `ms`.
* `values[proxy]` is `null` when there is no number, and `status[proxy]` says why: `unsupported` (the proxy cannot do it: no TLS or HTTP/2 listener, no WebSocket), `not_measured` (it could, but was not run), `invalid` (client errors: not publishable). A missing result is shown as unsupported or failed, never as zero.
* `at_conns` is the connection count of the best level (`null` for the memory tests, where the count is in the label).
* `flags`: `proxy_unsaturated` means the proxy used less than 90 % of its core at that level (the harness or the link set the number); `harness_saturated` means the origin or the sink was above 90 %. The editorial reading of such a point (for instance the link ceiling) is `campaign.json`'s `test_notes[<test id>]`.
* `conditions` is a sentence to print next to the number; the rest of the conditions (hardware, network, seed, repeats, noise, limits) is in `campaign.json`.
* `ktls[]` compares `tls.ktls = false` (`user_space`) with `true` (`ktls`) on rustle, on the tests of the TLS matrix.
* `proxies.json`: `version` is the one in the table of `FAIRNESS.md`; `repository` and `website` are optional `https` URLs, present only when `FAIRNESS.md`, `RESULTS.md` or `dut/<id>/Dockerfile` states them (a missing one is left for the author to add by hand). `characteristics` are facts quoted from `FAIRNESS.md` and `RESULTS.md`; there is no "does better" claim because nothing in the published results backs one.
* `docs/config.json`: `type` is `string`, `integer`, `boolean`, `duration` (a string such as `"1m"`), `string list`, `integer list` or `enum` (with `values`); `reload` is `live` (applied to new connections by `rustle reload`) or `restart`. Keys and defaults are read from the serde structs, `reload` from `restart_required()` / `effective()`, descriptions from `config::reference::KEYS`: adding a key without describing it, or changing a default without regenerating the files, fails `cargo test`. The file carries the rustle version, so a release commit regenerates it.

## Publishing a campaign

1. Create `bench/data/<id>/` (the same `<id>` as `bench/published/<id>/`) with a `campaign.json` and a `proxies.json` (copy the previous ones and edit: versions, hardware, `sources` pointing at the committed `published/<id>/runs/` indexes, `unsupported`, `test_notes`, `limits`), and add the campaign to `index.json` with `latest` set to it.
2. `make bench-publish` (or `REPORT_ONLY=1`) writes the charts, the README table and `bench/data/<id>/benchmarks.json` from the newest indexes (`CAMPAIGN=<id>` to target a folder other than `latest`); `make data` regenerates it from the committed `published/` runs. The date check stops you when `campaign.json` describes another campaign.
3. Review the diff, commit. `make data-check` must be clean.
