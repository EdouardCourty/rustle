# Data for the website

Structured copies of the published numbers, read by <https://github.com/EdouardCourty/rustle-site> (the source of <https://rustleproxy.dev>) at the latest release tag. The website never parses `README.md` or `RESULTS.md`: these files are the contract. They are committed, regenerated by tools, and checked by `make check` (`make data-check`), so they cannot go stale.

| File | What | Written by |
|---|---|---|
| `benchmarks.json` | every published number with its conditions | `tools/site-data.py --write` (`make data`), also run by `make bench-publish` |
| `campaign.json` | hand-edited input: hardware, network, which indexes make up the campaign, limits, notes | by hand, when a campaign is published |
| `proxies.json` | the competitors: version, tuning, protocols, characteristics | by hand, checked against `FAIRNESS.md` and `dut/*/Dockerfile` |
| [`../../docs/config.json`](../../docs/config.json) | reference of every config key | `UPDATE_CONFIG_DOCS=1 cargo test -p rustle config_reference` |

All files carry `schema_version` (currently `1`). An additive change (a new field) keeps the version; renaming, removing or changing the meaning of a field bumps it, and the website must refuse a version it does not know.

## `benchmarks.json`

Values come from the same campaign indexes and the same rule as the README table and the charts (`tools/benchlib.py`): for each test, the best sweep level without a client error. A number is never rounded up; the website formats it.

```text
schema_version  1
campaign        { name, date, commit, hardware{provider, generator, proxy, origin_sink}, network, software,
                  seed, repeats, run_seconds, proxy_cores, auth, noise_pct{min,max}, protocol, fairness, results }
proxies         ["rustle", "3proxy", "squid", "gost", "tinyproxy"]       order of the columns
tests[]         { id, transport, label, unit, direction, conditions, chart, note,
                  values{proxy: number|null}, at_conns{proxy: int|null},
                  status{proxy: "ok"|"unsupported"|"not_measured"|"invalid"},
                  flags{proxy: ["proxy_unsaturated"|"harness_saturated"]} }
scaling[]       { id, label, unit, direction, conditions, not_measured[proxy],
                  points[{ cores, values{proxy}, at_conns{proxy}, flags{proxy} }] }
ktls[]          { id, label, unit, direction, user_space, ktls }         rustle against itself, same ids as the tls tests
limits[]        { id, text }                                              what the benchmark does not cover
```

* `id` is `<transport>-<test>`, stable. `transport` is `plain`, `tls`, `tls-full-handshake`, `h2`, `ws` or `ws-tls`. The tests that have a chart in `docs/benchmarks/` name it in `chart`; the id and the chart file name match where it makes sense (`plain-1kb` / `plain-1kb.svg`; `plain-ram-25000` is `plain-ram.svg`).
* `direction` says which way is better (`higher` or `lower`). `unit` is `req/s`, `msg/s`, `Gbit/s`, `MB`, `µs/req`, `µs/msg` or `ms`.
* `values[proxy]` is `null` when there is no number, and `status[proxy]` says why: `unsupported` (the proxy cannot do it: no TLS or HTTP/2 listener, no WebSocket), `not_measured` (it could, but was not run), `invalid` (client errors: not publishable). A missing result is shown as unsupported or failed, never as zero.
* `at_conns` is the connection count of the best level (`null` for the memory tests, where the count is in the label).
* `flags`: `proxy_unsaturated` means the proxy used less than 90 % of its core at that level (the harness or the link set the number); `harness_saturated` means the origin or the sink was above 90 %. `note` (nullable) is the editorial reading of such a point, from `RESULTS.md` (for instance the link ceiling).
* `conditions` is a sentence to print next to the number; `campaign` holds the rest of the conditions (hardware, network, seed, repeats, noise).
* `ktls[]` compares `tls.ktls = false` (`user_space`) with `true` (`ktls`) on rustle, on the tests of the TLS matrix.

## `campaign.json`

Everything a result file cannot say: machines, network, software, the commit, the noise, and which indexes make up the campaign (`sources`, paths relative to `bench/`, normally the committed copy in `published/`). The seed, the number of repeats and the proxy core count are read from the runs themselves. `unsupported` lists proxies that cannot do a test (their runs are not published as numbers), `test_notes` the readings attached to a test id, `limits` the caveats.

A run dated more than a day from `date` is an error: never mix numbers from two campaigns.

## `proxies.json`

```text
proxies[]  { id, name, version, build, settings[], protocols{tls, h2, websocket}, characteristics[], fairness }
```

`version` is the one in the table of `FAIRNESS.md` and `protocols.tls` / `h2` the `# bench-ports:` line of `dut/<id>/Dockerfile`; `make data-check` fails when they disagree. `characteristics` are facts quoted from `FAIRNESS.md` and `RESULTS.md` (behaviours that explain a number); there is no "does better" claim here because nothing in the published results backs one.

## `../../docs/config.json`

```text
schema_version  1
version         the rustle version it describes (Cargo.toml)
tables[]        { name, description, keys[{ key, path, type, [values], default, description, reload }] }
```

`type` is `string`, `integer`, `boolean`, `duration`, `string list`, `integer list` or `enum` (with `values`). `default` is a JSON value (durations as `"1m"`). `reload` is `live` (applied to new connections by `rustle reload`) or `restart`. Keys and defaults are read from the serde structs, `reload` from `restart_required()` / `effective()`, and descriptions from `config::reference::KEYS`: adding a key without describing it, or changing a default without regenerating the file, fails `cargo test`. The version changes with every release, so a release commit regenerates it.

## Publishing a campaign

1. `make bench-publish` (or `REPORT_ONLY=1`): charts, README table and `bench/data/benchmarks.json` are written from the newest indexes. The date check stops you when `campaign.json` still describes another campaign.
2. Update `campaign.json`: `name`, `date`, `commit`, hardware, `sources` (point them at the new copy in `published/`), `unsupported`, `test_notes`.
3. Re-run `make data`, review the diff, commit. `make data-check` must be clean.
